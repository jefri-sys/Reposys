Executive summary

Reposys is a role-based reprography application. A React single-page client calls an Express API; MongoDB stores accounts, documents, orders and operational records; Socket.IO distributes live changes; a Windows Electron agent extends the system to local printer discovery and physical print submission.

Architectural reading

The core order-to-fulfilment path is implemented: upload → configuration → order → payment/cash confirmation → queue → staff/automation processing → pickup/tracking. Authentication (JWT + Bcrypt) IMPLEMENTED

What this feature is

A person creates an account, verifies their email, then signs in. The app remembers the signed-in person by using a secure HTTP-only cookie; it loads the current account before opening private screens.

How the user interacts

Register.jsx and Login.jsx collect identity and password details. The client shows validation or server messages, then AuthContext loads /api/auth/me and RootRedirect in App.jsx sends Students/Faculty to /dashboard, Staff to /staff and Admin to /admin.

Working - explained simply

The interaction begins in frontend/src/pages/auth/Register.jsx or frontend/src/pages/auth/Login.jsx. Their form state is submitted through the Axios client in frontend/src/services/api.js. backend/src/routes/auth.js maps registration to authController.register and protects login with authLimiter. backend/src/controllers/authController.js validates input, hashes passwords with bcryptjs when creating a User document, and signs a JWT with a configured expiry. It writes the token as an HTTP-only cookie. Later AuthContext.jsx calls GET /api/auth/me; verifyToken in backend/src/middleware/auth.js verifies the cookie, checks session invalidation and attaches the current user. The response updates React context, which redraws navigation and protected routes. Invalid, expired or missing tokens return 401 rather than opening the page.

What happens internally

Role approval is represented on User records: Faculty requests can be approved or rejected through Admin routes. Logout clears the cookie; the all-devices endpoint uses sessionInvalidatedAt so older issued tokens are rejected.

API and data flow

POST /api/auth/register, POST /api/auth/login, GET /api/auth/verify-email, GET /api/auth/me, POST /api/auth/logout; login/resend/reset paths use authLimiter.

Database impact

User: role, facultyRequestStatus, password hash, activeSessions, sessionInvalidatedAt, pushSubscription; never a plain-text password.

Realtime and notifications

No required Socket.IO event; React AuthContext is the client-side state transition.

Failure cases

Implemented: validation, invalid credentials, token expiry, malformed JWT, deleted user and invalidated session return explicit errors. Improvement: add account-lockout telemetry and automated authorization tests.

What this feature is

The system separates customer, counter-operation and management responsibilities, then places eligible orders into a fair priority queue.

How the user interacts

Students and Faculty place orders; Staff and Admin see and process the queue. Admin can reorder a queued item with a reason.

Working - explained simply

After orderController.createOrder receives the user role, it calls calculatePriorityScore and calculateEstimatedDuration in backend/src/utils/orderHelpers.js. queueService.js reads active orders, separates service queues and sorts them by priority/age/workload. AdminDashboard.jsx can call the queue reorder route; the controller records the reason, saves the order and emits queue_update.

What happens internally

Order stores priorityScore and estimatedDuration. QueueService uses serviceType, status, createdAt and workload to calculate position and wait time. Starvation prevention runs from the scheduled jobs module.

API and data flow

Database impact

Realtime and notifications

Failure cases

Implemented: service queue filters, duration summation and reorder validation. Improvement: make multi-instance reorder/claim operations atomic.

Document Upload with AI Analysis IMPLEMENTED

What this feature is

Before ordering, a user supplies a file. The system stores its metadata, can inspect the document, and lets the order wizard reuse the uploaded record instead of placing a raw browser file inside an order.

How the user interacts

WizardStep1Upload.jsx and DocumentUpload.jsx show file selection, upload progress, previews and error messages. The document library can return a controlled URL for a previously uploaded item.

It returns the document identifier to React state. The next wizard step carries that identifier; the order route later reads the same Document record. GET /api/documents/:id/url returns a server-authorized document URL rather than exposing the model directly.

Realtime and notifications

Upload itself is request/response based; later order status uses realtime events.

Failure cases

Implemented: upload middleware and controller propagate bad file, timeout and storage failures to the global error handler. Improvement: state a maximum size/type policy in a shared validation module and test malicious-file cases.

Realtime and notifications

Payment System (Razorpay, Cash, Retry, Coupons and Receipts) IMPLEMENTED

What this feature is

The platform supports an online payment provider, a stored wallet balance and a cash-at-counter route. A payment success is checked by the server before the order is treated as paid.

How the user interacts

WizardStep3Payment.jsx opens Razorpay for online payments or selects wallet/cash options. WalletPage.jsx and WalletTopup.jsx show balance and transactions. StaffDashboard.jsx has the cash collection action.

Working - explained simply

The browser starts in frontend/src/components/user/WizardStep3Payment.jsx or frontend/src/pages/WalletTopup.jsx. The former requests POST /api/payments/create-order and returns the provider order information; the client payment callback then posts to /api/payments/verify. backend/src/routes/payments.js applies verifyToken to these customer operations, while paymentController.verifyPayment validates the signature before writing Payment and Order state. The webhook route uses raw JSON and handleWebhook verifies the webhook signature. Wallet top-ups similarly route through walletController.createTopupOrder and verifyTopup, updating Wallet and WalletTransaction. Cash is not accepted by the customer browser as proof of payment: staffController.collectCash is guarded in backend/src/routes/staff.js by verifyToken plus allowRoles(Staff, Admin), then raises the CASH_CONFIRMED event.

What happens internally

14 • Discussion

Viva/client discussion questions

  1. How does a customer order work? Start at OrderWizard, follow upload/estimate/create routes to orderController and Order, then show payment and staff queue transitions.
  2. What actually protects an Admin API? App.jsx navigation is helpful, but backend routes apply verifyToken and roleGuard(Admin).
  3. How does live tracking work? Track joins public-track:<orderId>; controllers/queue code emit updates through Socket.IO after state changes.
  4. Why is the Electron agent needed? Browser code cannot safely enumerate or submit Windows printer jobs. The agent reports printers and receives print_job events.
  5. Does the automatic countdown edit an order? No. It displays saved autoProcessAt; server cron rechecks state and changes an eligible due order.
  6. How are payments trusted? Razorpay response/webhook signatures are verified server-side before Payment/Order status is accepted.
  7. What would you improve before production? Per-agent credentials, socket authorization, public tracker token, atomic job claims, rate limiting and integration tests.
  8. How do files relate to orders? Upload creates Document metadata; Order references document IDs; PrintJob later references the documents required for fulfilment.

Two-minute non-technical explanation

Reposys is a digital print-centre workflow. Customers upload a file and choose how they want it printed. The system calculates a price, records payment, keeps the order in a queue and lets staff process it. Customers can watch progress and receive notices. Administrators control people, prices, stock and reports. For physical printing, a small application on a Windows machine talks safely to the website and sends work to local printers. The source code contains these workflows, but the security and reliability improvements in this report should be completed before calling it production-hardened.

Executive, technical and academic conclusion

Executive conclusion

The project contains a broad, source-backed reprography workflow rather than a presentation-only interface. Its major customer, staff, administration, notification and print-agent paths are present and connected.

Technical conclusion

The architecture is a pragmatic React/Express/MongoDB system with Socket.IO and a separate Electron boundary for operating-system printing. The strongest next step is not more features: it is hardening identity/rooms, secrets, public tracking and distributed automation, then verifying those controls with tests and operational monitoring.

Academic conclusion

This audit intentionally distinguishes observed implementation from recommendations. Every detailed feature names actual files and explains the action-to-data-to-UI sequence. This makes it suitable for a viva, client walkthrough or future engineering handover without claiming functionality that the repository does not prove.
